# Архитектура ИИ-агентов проекта (Antigravity Multi-Agent Workflow)

Данный документ описывает процесс разработки в этом репозитории на базе среды Antigravity по концепции **Spec-First**.
В системе работают три скомбинированных ИИ-агента, каждый из которых выполняет свою специфическую роль для оптимизации стоимости, контекста и качества кода.

## 👥 Роли ИИ-агентов в команде

### 1. 🚀 Kimi (Роль: Senior Software Engineer / Главный двигатель)
**Уровень:** 3-4 по шкале использования ИИ (Продвинутый агент / Автономный исполнитель).
**Обоснование:** Kimi обладает высокой способностью к рассуждению (reasoning) на уровне Senior-разработчика. Экономика позволяет использовать его в продолжительных циклах `Plan -> Act -> Observe -> Reason -> Repeat` без оглядки на бюджет.
**Обязанности (пишет 99% кода):**
*   **Проектирование и код:** Самостоятельное проектирование БД, написание сложной бизнес-логики, алгоритмов и интеграций. Никакого отношения как к джуну — Kimi решает нетривиальные задачи.
*   **Глубокая отладка:** Автономный запуск в терминале (Bash), чтение логов ошибок, поиск причин падения кода и их исправление.
*   **Self-Review и Рефакторинг:** Написание тестов (TDD), прогон линтеров, самостоятельный рефакторинг собственного кода до достижения идеального состояния перед пушем.
*   **Управление субагентами:** Kimi может порождать клонов (субагентов Kimi) для параллельного выполнения задач (например, один Kimi-Senior пишет бэкенд, второй параллельно делает сложный UI на фронтенде).

### 2. 👨💻 Claude 3 Opus (Роль: ИИ-CTO / Visionary)
**Уровень:** 4 (Архитектор).
**Обоснование:** Самый высокий IQ, но критически дорогие токены. 
**Обязанности (Не пишет код!):**
*   **Создание Spec-first контекста:** Перевод сырых бизнес-требований от стейкхолдеров в строгий и выверенный PRD (Product Requirements Document).
*   **Формирование Rules:** Написание и обновление глобальных инструкций (`.claudecode`, `.cursorrules`) на основе выявленных ошибок.
*   **Финальный архитектурный Gatekeeper:** Чтение только итогового Git Diff (чтобы не тратить токены на весь контекст) для проверки безопасности и соответствия глобальной архитектуре.

### 3. 🧠 Gemini (Роль: Context Manager / Библиотекарь)
**Уровень:** 2-3 (Инструмент маршрутизации).
**Обоснование:** Контекст от 1 до 2 млн токенов. Не пишет код, потому что Kimi сделает это лучше и дешевле. Задача Gemini — избавить Kimi от необходимости читать весь репозиторий (решение проблемы "иголки в стоге сена").
**Обязанности:**
*   **Маппинг репозитория:** Загрузка всей кодовой базы, логов и старой документации.
*   **Поставка контекста для Kimi:** Когда Kimi приступает к задаче, Gemini делает семантическую выборку и выдает Kimi только те файлы и зависимости, которые нужны для работы прямо сейчас.

## 🔄 Agentic Pipeline: Как фича проходит по конвейеру

Процесс выстроен так, чтобы вся тяжелая интеллектуальная работа ложилась на плечи Kimi.

**Шаг 1: Видение и Спецификация (CTO — Claude Opus)**
1. Человек формулирует бизнес-задачу.
2. Claude Opus анализирует запрос и генерирует высокоуровневый PRD, описывающий архитектурный подход, крайние случаи (edge cases) и требования к безопасности.
3. *[Human in the loop: Человек утверждает PRD]*

**Шаг 2: Сборка рабочего пакета (Context Manager — Gemini)**
1. Gemini «проглатывает» PRD от Opus и весь репозиторий проекта.
2. Он находит все связанные файлы (модели, контроллеры, компоненты) и собирает компактный "Контекстный пакет" (Context Package).
3. Этот пакет передается Kimi, чтобы тот не тратил свои токены на чтение лишнего мусора.

**Шаг 3: Автономная разработка (Senior — Kimi) — ОСНОВНОЙ ЭТАП**
1. Kimi получает PRD и Контекстный пакет.
2. Kimi переходит в режим агента для работы над задачей в среде и начинает непрерывный цикл:
   * **Plan:** Строит технический план реализации сложной фичи.
   * **Act:** Пишет код, используя MCP для доступа к файловой системе и БД. Запускает команды через Bash-терминал.
   * **Observe:** Запускает компиляцию/тесты, видит ошибки в логах.
   * **Reason:** Как Senior-инженер, анализирует логи, понимает, где нарушена логика или совместимость.
   * **Repeat:** Переписывает код, пока всё не заработает идеально.
3. Если задача огромная, Kimi распараллеливает её на своих субагентов (другие сессии Kimi). Kimi самостоятельно пишет сложные мок-тесты, интеграционные тесты и проверяет код-стайл.

**Шаг 4: Двойное ревью и Merge**
1. Kimi делает Self-Review своего кода.
2. Gemini быстро прогоняет измененные файлы по всему огромному контексту проекта (не сломает ли это что-то на другом конце приложения?).
3. Финальный Git Diff отправляется Claude Opus. Opus выступает как техдир: он не ищет пропущенные запятые, он смотрит, не внедрил ли Kimi уязвимость и правильный ли паттерн использован.
4. *[Human in the loop: Человек делает Merge]*

## 🛑 Глобальные правила кодирования (Golden Rules)
*   **Типизация:** Строгая. `any` строго запрещен.
*   **Безопасность:** Всегда валидировать DTO, не доверять входящим данным.
*   **Отчетность:** После завершения всех шагов изменения документируются.

## 🛠️ Арсенал навыков ИИ-агентов (Skills Toolkit)

### 1. 🚀 Арсенал навыков Kimi (Senior-исполнитель)
**Цель:** Дать Kimi возможность делать всё, что делает Senior-разработчик локально на своем рабочем месте, не отвлекая человека.

**💻 Базовые навыки работы со средой (CLI & File System)**
*   `execute_bash_command`: Выполнение любых команд в терминале (запуск сервера, установка пакетов, компиляция). Kimi сам читает stderr, если команда упала, и сам исправляет ошибку.
*   `edit_file_by_diff`: Умение заменять конкретные строки в файле, а не переписывать весь файл целиком (экономит токены и время).
*   `regex_search_replace`: Массовая замена паттернов по всему проекту (например, при рефакторинге названия метода во всех контроллерах).

**🧪 Навыки тестирования и QA (Self-Correction Loop)**
*   `run_tests_and_fix`: Запуск тестовых фреймворков. Если логи красные, автоматический анализ ошибок и переписывание кода до "зеленого" состояния.
*   `run_linter`: Проверка кода линтерами (ESLint/Ruff) перед пушем с самостоятельным исправлением предупреждений.
*   `browser_automation`: Использование Playwright/Puppeteer MCP. Если Kimi делает UI, он открывает headless-браузер, делает скриншоты и проверяет верстку на наличие проблем.

**🗄 Навыки работы с инфраструктурой (Database MCP)**
*   `execute_sql_query`: Выполнение тестовых SQL-запросов (SELECT/INSERT) для проверки правильности сложных JOIN'ов логики миграций.
*   `inspect_db_schema`: Получение актуальной структуры таблиц из БД, чтобы опираться на реальные данные при разработке.

**🌐 Внешние интеграции**
*   `fetch_library_docs`: Использование Web Search (Context 7) для поиска документации по актуальным версиям библиотек, которых не было в обучающих данных модели.

**📝 Навыки рефлексии и памяти**
*   `save_lesson_learned`: Если на баг ушло много итераций (например, конфликт версий), после починки Kimi генерирует отчет (Lessons Learned) и сохраняет его в файл `.agent_memory.md`. В следующий раз Kimi обращается к этому файлу, чтобы решить похожую задачу с первой попытки.
*   `read_agent_memory`: Перед началом работы над задачей Kimi обязан прочитать `.agent_memory.md` и учитывать накопленные уроки.

### 2. 🧠 Арсенал навыков Gemini (Context Manager)
**Цель:** Быстрая навигация по огромным массивам данных и подготовка «чистого» контекста для Kimi.

**📂 Навыки глубокого поиска (Deep Search)**
*   `semantic_code_search`: Поиск по кодобазе по смыслу, а не по тексту (например: «найти где начисляются скидки»).
*   `build_dependency_graph`: Анализ AST. Gemini строит граф зависимостей и предупреждает: «Если изменить этот класс, сломаются вот эти компоненты». Этот граф передается Kimi.
*   `parse_massive_logs`: Анализ объемных логов с продакшена. Способность найти stack trace в гигантском дампе и выдать Kimi чистую причину падения с переменными окружения.

**📦 Навыки упаковки**
*   `generate_context_bundle`: Сбор нужных файлов в 1 текстовый пакет. Gemini берет PRD, находит 5-10 связанных файлов, склеивает их и говорит Kimi: «Вот всё, что нужно для работы, остальное не трогай».

### 3. 👨💻 Арсенал навыков Claude Opus (ИИ-CTO)
**Цель:** Высокоуровневая архитектура, безопасность и стандарты. Не тратит токены на рутину.

**📝 Навыки Solution-архитектуры**
*   `generate_prd`: Принимает бизнес-задачу (например: «Хочу авторизацию через Telegram») и генерирует структурированный Markdown-документ (архитектура, API, схемы БД).
*   `update_system_rules`: Анализирует паттерны ошибок Kimi и обновляет глобальные инструкции (`.claudecode` или `.cursorrules`), чтобы предотвратить их в будущем.

**🛡 Навыки Gatekeeper'а (Review)**
*   `analyze_git_diff`: Читает только измененные строки кода (Diff), минуя весь проект.
*   `security_audit_check`: Поиск уязвимостей (SQL-инъекции, XSS, логические дыры) в коде перед финальным мержем.

## 🎓 Дообучение в нашей системе (Continuous Agent Learning)

Процесс эволюции агентов делится на два уровня: динамическое (через контекст и память) и глубокое (Fine-Tuning модели).

### Уровень 1: Динамическое дообучение (In-Context Learning & Memory)
Агенты обучаются в реальном времени, пополняя базу знаний проекта. Это работает через специальные навыки рефлексии и обновления правил.

1.  **Саморефлексия Kimi (Post-Mortem):**
    *   У Kimi есть навык `save_lesson_learned`. Если на баг ушло много итераций (например, конфликт версий), после починки он генерирует отчет (Lessons Learned) и сохраняет его в файл `.agent_memory.md`. В следующий раз Kimi обратится к этому файлу, чтобы решить похожую задачу с первой попытки.
2.  **Обновление глобальных правил (Claude Opus):**
    *   Если Opus видит при ревью систематическую ошибку Kimi, он использует навык `update_system_rules`. Opus перезаписывает файл правил (`.cursorrules` или `.claudecode`), жестко фиксируя новое правило. Каждый новый клон Kimi будет инициализироваться с этим знанием.
3.  **Индексация решений (Gemini):**
    *   Gemini выступает как векторная база памяти. После каждого успешного Merge, Gemini индексирует PR (Product Requirement) и финальный Git Diff. Теперь при похожих фичах Gemini выдаст Kimi этот старый код как «идеальный пример для подражания» (Few-Shot Prompting).

### Уровень 2: Глубокое дообучение (Fine-Tuning Senior-исполнителя)
Так как токены Claude Opus слишком дороги для экспериментов, а Gemini работает как векторный поисковик/оркестратор, основным объектом для классического файнтюнинга становится Kimi. Цель — превратить его из "просто Senior-разработчика" в "Senior-разработчика, который 5 лет пишет код именно в нашей компании".

**Пайплайн Fine-Tuning'а для Kimi:**
1.  **Сбор Датасета (Data Pipeline):** Раз в неделю собирается информация о коде:
    *   Написан Kimi.
    *   Успешно прошел все тесты.
    *   Получил высокий балл при код-ревью от Claude Opus или Gemini.
2.  **Форматирование:** Эти PR преобразуются в структурированные пары: `[Задача (PRD)] -> [Идеальный код (Diff)]`.
3.  **Обучение (SFT / LoRA):** На этих данных запускается дообучение (Supervised Fine-Tuning) базовой модели Kimi.
4.  **Результат:** Переход проекта на новую кастомную версию модели, натренированную на архитектурных паттернах конкретной кодовой базы.
